# 同日相集與 ISO 日期修正

沒有指定拍攝日期的正常上傳，帳戶 API 會以原有建立時間回傳 ISO 日期，例如 `2026-10-17T07:44:01.123Z`。舊前端只在空白處切開日期，因此同一天不同秒的四份上傳被拆成四張單獨卡片，沒有「進入相集」入口；直接以完整 ISO 字串開相集也不符合日期參數規格。這次完整頁面／正常 worker 演練實際重現了問題。

新版 `2026.10.17-ui.95.10` 共用 `photoCalendarDay`：沒有時區的拍攝日期保留原年月日，含時區的時間及上傳時間改用裝置顯示的本地年月日。時間軸分組、相集連結、跨頁讀取過濾、相集日期／年齡及移動目的清單都使用同一規則；分組排序／標題使用該日的本地中午，避免只有日期的字串被 UTC 解讀成前一天。這是讀取與分組修正，沒有批次改寫照片日期、原檔、帳戶或上傳收據。

同時更新四頁對相關腳本的版本引用。H圖示、CSS及原生帳戶／傳輸程式未改；原 test.95 R4 APK與來源保留，R4不含這次修正，暫不作新的分發候選。

本輪檢查：

- 修前實際正常上傳四份後仍是四張單張卡片；修前來源的分組負向測試亦失敗。失敗及原來源保留。
- 台北、UTC、洛杉磯各21項日期／實際相集分頁讀取檢查，涵蓋空白／T分隔、時區跨日、閏日、上傳日期後備及精確ID過濾。
- 現行照片模式與相集模式各一組日期操作回歸，保留取消、全失敗、部分失敗及只重試失敗項的真實前端／HTTP／SQLite流程；供應者為人工服務。
- 完整本機旅程九組通過：從實際表單註冊兩個普通帳戶、建立三個虛擬相簿，儲存／重載生日，批量／單檔標籤模式的四份正常上傳，同日相集合併與開啟、三張圖片解碼、兩秒影片播放、四份原檔逐byte下載、標籤、移動日期／相簿、B拒絕讀取A資源、四份媒體刪除、舊URL清除及兩帳戶刪除查詢完成。
